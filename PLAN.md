# clean — a native mail app for Omarchy

**Plan v1 · 18 Nov 2026**

A private, fast desktop mail client with the calm three‑pane layout from the reference
screenshots, a first‑run setup for appearance and account, three theme modes
(**White**, **Black**, **Omarchy**), and Apple‑quality motion. Rust + GPUI Kit.

## 4. Theme system — the heart of the app

### 4.1 Modes

`ThemeMode { Light, Dark, Omarchy }` — user‑facing names **White**, **Black**, **Omarchy**.

| Token | White | Black | Omarchy (live) |
|---|---|---|---|
| canvas | `#F5F5F7` | `#0B0C0E` | `background` `#2d353b` |
| surface | `#FFFFFF` | `#121316` | `background` |
| sidebar | `#F0F0F3` | `#0E0F12` | `dark_background` `#21272c` |
| raised | `#FFFFFF` | `#191B1F` | `lighter_background` `#343f44` |
| inset | `#ECECF0` | `#08090B` | `darker_background` `#181d20` |
| text | `#1D1D1F` | `#F5F5F7` | `foreground` `#d3c6aa` |
| muted | `#6E6E73` | `#A1A1A6` | `light_foreground` `#9da9a0` |
| faint | `#8E8E93` | `#6E6E73` | `dark_foreground` `#4f585e` |
| border | `#E3E3E8` | `#23252A` | `muted` `#475258` |
| selection | accent 12 % | accent 22 % | `selection` `#3d484d` |
| danger | `#D70015` | `#FF453A` | `red` `#e67e80` |
| success | `#1A7F37` | `#30D158` | `green` `#a7c080` |
| warning | `#B25000` | `#FF9F0A` | `yellow` `#dbbc7f` |

Derived Omarchy states follow Omarchy's own template recipe:
`hover = mix(dark_background, foreground, 6%)`,
`active = mix(dark_background, accent, 18%)`, `border = muted`.
Alpha values in the live `colors.toml` are respected.

**Omarchy mode is not a lookalike.** It parses
`~/.local/state/omarchy/current/theme/colors.toml` at startup, maps the tokens above,
and watches the file. When you switch Omarchy themes (Everforest → Catppuccin → …),
`clean` crossfades to the new palette within a second. No config file to edit, no
`omarchy-theme-set-clean` hook required. A manual **Reload Omarchy theme** button
lives in Appearance.

If the active Omarchy theme is light (`mode = "light"`), surface roles adapt while the
token mapping stays identical, so the app still matches the desktop.

### 4.2 Accent

- Default is **Blue**. In White/Black: `#007AFF` / `#0A84FF`. In Omarchy: the live
  theme's `blue` token (`#7fbbb3` for Everforest), so the app belongs on the desktop.
- Swatches shown in setup and Settings: Blue (default), Omarchy, Violet, Pink, Red,
  Orange, Yellow, Green, Teal, Graphite, plus **Custom…** hex.
- One accent is stored. Contrast is corrected per mode (light mode darkens the hue
  until text on the accent passes 4.5:1; dark mode keeps it luminous).
- Accent drives: primary buttons, focus rings, selection bar, unread dot, links,
  date chip, toggle thumb, slider fill, and the onboarding checkmark.

### 4.3 Persistence

`~/.config/clean/config.toml`

```toml
[appearance]
mode = "omarchy"        # light | dark | omarchy
accent = "blue"         # named swatch or "#RRGGBB"
text_scale = 1.0
reduce_motion = false

[window]
width = 1440
height = 900

[onboarding]
complete = true
```

Secrets never go here — they go to the Secret Service (`oo7`), service `clean`,
attribute `account=<id>`.

### 4.4 Theme implementation

- `src/theme/palette.rs`: a `Palette` struct of semantic tokens (`Color`), plus
  `mix()`, `alpha()`, and contrast correction.
- `src/theme/omarchy.rs`: parse `colors.toml`, map tokens, watch with `notify`
  (debounced 150 ms) on `~/.local/state/omarchy/current` and the theme file.
- `src/theme/accent.rs`: named swatches, custom hex, per‑mode adjustment.
- A `CleanTheme` GPUI global layered over GPUI Kit's `ActiveTheme`; components read
  `cx.theme()` for motion tokens and our semantic palette for color.
- Theme switch = interpolate every token over 220 ms; no layout shift, no flash.
- Omarchy changes stream from a background thread to the UI entity; the UI never
  blocks on disk.

## 5. First run and sign‑in

### 5.1 Flow

```
Launch
  └─ first run? ── no ──► Inbox
        │
        yes
        ▼
  ① Appearance           ② Account              ③ Connect              ④ Sync
  "Make it yours."       "Bring your mail."     provider sheet         progress → inbox
  White / Black /        Google / Proton /      OAuth or IMAP          animated check
  Omarchy cards          Apple                  credentials
  accent swatches
        └──────────────────────────────────────────────────────────────►
```

**① Appearance** — 1000 × 700 window, centered 760 px column.
- Wordmark fades + rises 8 px over 500 ms.
- Three live miniature app previews (real palette, real type, not screenshots):
  sidebar + list + reader. Hover lifts 1 px; selection uses a 380 ms spring,
  1.02 scale, 2 px accent ring, animated check.
- Accent swatches below; the selected swatch springs to 1.08 and shows a white check.
- `Continue` primary button (accent), `Skip for now` text button.
- Choosing a mode immediately re‑skins the preview and the whole setup window.

**② Account** — provider cards with official marks:
- **Google** — Gmail + Google Calendar.
- **Proton** — Proton Mail via Proton Bridge.
- **Apple** — iCloud Mail.

**③ Connect** — provider‑specific sheet (see §7):
- Google: system browser OAuth, loopback + PKCE, return → "Connected as …".
- Proton: Bridge detection + host/port/user/password, "Test connection".
- Apple: Apple ID + app‑specific password, "Test connection".
- Errors are inline, human, never raw IMAP strings. Retry with a gentle shake (120 ms,
  2 px) and a clear hint.

**④ Sync** — folder discovery with a staggered checklist (Inbox, Sent, Drafts,
Archive, Spam, Trash), progress ring, then a 420 ms drawn checkmark and the inbox
crossfades in.

### 5.2 Motion language (Apple‑like, restrained)

| Moment | Spec |
|---|---|
| Window open | 220 ms opacity + 8 px rise |
| Step transition | out 160 ms fade/8 px, in 280 ms rise 16 px, `cubic-bezier(.22,1,.36,1)` |
| Staggered items | 35 ms delay per item, max 6 |
| Theme card select | spring 380 ms, damping 0.80, scale 1.02, ring 2 px |
| Accent swatch | hover 120 ms 1.12; select spring 1.0 |
| Button press | 0.97 scale 90 ms; release 240 ms spring |
| List row select | 160 ms background, 2 px spring bar |
| Sheet / dialog | scrim 180 ms; panel 320 ms `translateY(24→0)` + `scale(.98→1)` |
| Theme switch | 220 ms color interpolation |
| Success check | 420 ms stroke draw + spring |
| Reduced motion | snaps, fades only, no spatial movement |

Motion tokens live in one place (`duration_fast 120`, `normal 220`, `slow 320`;
`easing_enter/exit/move`; `spring_control`, `spring_move`) and are wired through
GPUI Kit's `motion_tokens()` so every control shares the same feel.

## 6. Architecture

Single binary crate first; extract crates only if compile times demand it.

```
Cargo.toml
assets/
  fonts/            Inter, Instrument Serif, JetBrains Mono (bundled, OFL)
  brand/            clean wordmark + app icon (SVG)
src/
  main.rs
  app.rs            app shell, routes, global state
  theme/
    mod.rs
    palette.rs
    accent.rs
    omarchy.rs
  ui/
    titlebar.rs
    sidebar.rs
    mail_list.rs
    reader.rs
    composer.rs
    calendar_rail.rs
    settings.rs
    command_palette.rs
    onboarding/
      mod.rs
      appearance.rs
      account.rs
      connect.rs
      sync.rs
  mail/
    mod.rs
    account.rs
    provider.rs
    imap.rs
    smtp.rs
    oauth.rs
    sync.rs
    mime.rs
  storage/
    mod.rs
    db.rs
    config.rs
    secrets.rs
  assets.rs
```

**Threading:** GPUI owns the UI thread. A dedicated mail engine thread runs a Tokio
runtime for IMAP/SMTP/OAuth; it talks to the UI through `async_channel` and GPUI
tasks. The UI never blocks on network or disk.

**State:** `Entity<AppState>` + feature models. No global mutable state except the
theme and config globals.

**Cache:** `~/.local/share/clean/clean.db` (SQLite WAL, FTS5). Tables: accounts,
folders, messages, bodies, labels, drafts, sync_state. Cache‑first rendering:
open → instant inbox from disk → background refresh.

**Dependencies (planned):**
`gpui-kit 0.10`, `serde`, `toml`, `rusqlite` (bundled), `async-imap`, `lettre`,
`oauth2`, `reqwest` (rustls), `oo7`, `notify`, `chrono`, `tracing`,
`tracing-appender`, `html2text`, `mailparse`.

**Security:** credentials in Secret Service; TLS required; no plaintext passwords on
disk; OAuth refresh tokens encrypted by the keyring; HTML mail rendered sandboxed
with remote images blocked by default; no telemetry.

## 7. Provider support — honest matrix

This is the part that needs to be clear before we build it.

| Provider | What actually works | What we build | Blocker |
|---|---|---|---|
| **Google / Gmail** | Gmail API or IMAP/SMTP with OAuth 2.0 | Browser OAuth (PKCE + loopback), XOAUTH2 IMAP/SMTP, refresh token in keyring | Needs a Google Cloud **Desktop OAuth client ID**. For personal use, add yourself as a test user. Public distribution of Gmail scopes requires Google verification. |
| **Proton Mail** | No public IMAP/SMTP API. Only **Proton Mail Bridge** (paid plans) exposes localhost IMAP/SMTP. | Bridge wizard: detect `127.0.0.1:1143/1025`, enter Bridge credentials, test, sync | Direct Proton sign‑in is not possible for third‑party apps. We will not fake it. |
| **Apple / iCloud** | IMAP `imap.mail.me.com:993` + SMTP `smtp.mail.me.com:587` with an **app‑specific password** | Apple ID + app‑specific password form, keyring storage, connection test | "Sign in with Apple" does **not** grant mail access. The UI says **iCloud Mail** and links to appleid.apple.com to create the password. |

Calendar:
- Google Calendar via the same OAuth token (`calendar.readonly`) in phase 5.
- Apple/Proton calendar: ICS subscription or local `.ics` first; native CalDAV later.

The sign‑in UI is built in milestone 3 regardless; the engine lands provider by
provider so failures are isolated.

## 8. Milestones — accounts first

The mail engine is headless and testable from the CLI before the full UI exists. This
de-risks OAuth, IMAP, SMTP, and the keyring early, and means the first time the inbox
window appears it is showing real mail.

### M0 — Toolchain spike (½ day)
- Install optional `vulkan-validation-layers`; confirm Vulkan on NVIDIA/Wayland.
- `cargo init --name clean`, add `gpui-kit = "0.10.0"`, open a window with the wordmark.
- Bundle fonts; verify text rendering and 60 fps.
- Add optimized dev profile for GPUI deps.
- **Done when:** `cargo run` opens a 1440 × 900 window with correct fonts on this machine.

### M1 — Mail engine, headless (4–6 days)
- `config`, `secrets` (Secret Service), `db` (SQLite WAL + FTS5), `provider` trait.
- IMAP (`async-imap`), SMTP (`lettre`), OAuth 2.0 PKCE + loopback, XOAUTH2.
- Folder discovery, header fetch, body on demand, cache‑first sync, offline reads.
- CLI for headless testing:
  `clean auth google`, `clean auth apple`, `clean auth proton`,
  `clean sync`, `clean status`, `clean search "term"`.
- Local mock IMAP/SMTP fixtures for tests; no real credentials needed in CI.
- **Done when:** a test account syncs folders, headers, and bodies; tokens survive a
  restart; the same data is readable offline; `clean search` is instant.

### M2 — Onboarding shell + connect UI (2–3 days)
- Minimal GPUI window, theme engine (needed for setup), wordmark, fonts.
- Appearance screen: White / Black / Omarchy cards, live previews, accent swatches.
- Account screen: Google / Proton / Apple cards.
- Connect sheets wired to the M1 engine, with test‑connection, inline errors, and the
  sync checklist.
- **Done when:** you can choose a theme and accent, connect a real account, watch it
  sync, and land in a placeholder inbox — all in the real app.

### M3 — Full inbox UI (3–4 days)
- Titlebar, sidebar, list, reader, reply bar, settings sheet, calendar rail.
- Resizable panes, keyboard nav, command palette, loading/empty/error states.
- Demo data for offline visual QA, replaced by the M1 cache.
- **Done when:** it matches the reference structure at 1440 × 900, scrolls at 60 fps,
  and every control has hover/focus/press states.

### M4 — Compose, reply, send, drafts (2 days)
- SMTP send, reply/forward with quoting, attachments v1, autosaved drafts,
  Sent/Drafts folders, undo send (5 s).
- **Done when:** a round‑trip send arrives and the thread renders correctly.

### M5 — Calendar rail + event sheet (2–3 days)
- Upcoming rail visual + demo events in M3; wire Google Calendar or ICS here.
- New Event sheet, date detection chip in mail, add‑to‑calendar.
- **Done when:** events appear in the rail and a detected date can be added in one click.

### M6 — Packaging + polish (1–2 days)
- Arch `PKGBUILD`, `.desktop`, SVG icon, install/uninstall docs.
- Notifications, unread badge, single‑instance, autostart option.
- Unit tests (palette, MIME, config) + GPUI interaction tests for onboarding.
- Release build, `strip`, size check.
- **Done when:** `clean` launches from the Omarchy launcher, follows the theme, and
  installs with one `makepkg -si`.

Estimated total: **2–3 focused weeks**.

## 9. Risks and mitigations

| Risk | Mitigation |
|---|---|
| GPUI Kit is pre‑1.0; APIs may move | Pin `0.10.0` + `Cargo.lock`; keep GPUI usage behind `ui/` and `theme/` |
| Heavy first build on 11 GiB RAM | `CARGO_BUILD_JOBS=8`, `lld`/`mold`, optimized dev profile, build once then iterate |
| Google OAuth verification | Personal test‑user mode first; document the client‑ID setup; allow a user‑supplied client ID |
| Proton has no direct API | Bridge‑only, stated in the UI; no misleading "Sign in with Proton" button |
| Apple "Sign in with Apple" ≠ mail | Label it iCloud Mail + app‑specific password, with a help link |
| NVIDIA/Wayland rendering quirks | Test on this machine first; keep X11 fallback; validation layers during development |
| Design likeness / branding | Original name, wordmark, mascot, copy, icons; layout inspiration only |
| HTML mail security | Sandboxed renderer, remote images off, no scripts, link confirmation |

## 10. Decisions

### Resolved
1. **Build order:** accounts first. Headless mail engine (M1), then the setup/connect
   UI (M2), then the full inbox (M3).
2. **Accent in Omarchy mode:** default **Blue** follows the live Omarchy blue
   (`#7fbbb3` on Everforest). Other swatches and custom hex still override it.
3. **Calendar:** the Upcoming rail and event sheet are built visually in M3 with demo
   events; real calendar data is wired in M5.
4. **Name:** `clean`, lowercase wordmark, binary `clean`, app ID `dev.alvyn.clean`.

### Credentials you will provide at connect time (never in chat)
- **Google:** a Desktop OAuth client ID + secret from your own Google Cloud project.
  The connect sheet has a "Use your own OAuth client" section and a link to the
  console. For personal use, add your address as a test user.
- **Proton:** Proton Mail Bridge running locally, plus the Bridge username/password
  it shows. `clean` auto-detects `127.0.0.1:1143` and `1025`.
- **Apple:** Apple ID + an app-specific password generated at appleid.apple.com.

All three are stored in the Secret Service, never in `config.toml`.
